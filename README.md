# AgentCrew V2.3（Tauri + Vue3 + SQLite）

AgentCrew 是一个**本地优先、轻量、串行**的多 Agent 代码开发编排桌面工具。V2 新增了外部存储、定时执行、任务/问答双通道、运行中需求修改、浅色/深色主题，以及更适合阅读的 Agent 会话与工具调用日志。V2.2 支持任务完成后的「追加需求」：评审者先做增量梳理，简单改动只生成 1 个子任务，避免每次都重新拆解和过度设计。

当前版本内置两类基础角色，后续可扩展更多角色：

- **评审者 Reviewer**：负责拆解需求、代码 diff 评审、摘要校验、全局收口。
- **编码者 Coder**：通过 **Harness CLI（`dsh`）** 调用其自带的 `read_file / write / bash / git` 工具，在真实项目目录中写代码。

应用本身只负责：配置管理、任务拆解、状态机调度、prompt 组装、diff 捕获、评审 JSON 解析、SQLite 归档、人工兜底。**不实现**内置编辑器/终端、MCP 插件市场、自动 git 冲突合并、复杂依赖拓扑、多用户、RAG。

## 1. 功能总览

| Tab | 功能 |
| --- | --- |
| Agent 配置 | 新增/编辑/删除/导入/导出 Agent；绑定角色、服务商、model、baseUrl、apiKey、systemPrompt、temperature |
| 任务列表 | 历史任务卡片、新建任务弹窗、打开详情、删除任务、已完成任务直接「追加需求」 |
| 任务工作台 | 第一屏：**迭代（版本）列表**（按版本倒序，含需求/时间/任务数/耗时/token）；进入迭代后三栏：左：迭代树 + 子任务 +「查看/设计」；中：**方案与契约入口 + 评审者与 Coder 完整对话时间线**（工具调用默认收起）+ 人工消息；右：**预览面板**（设计方案 / 摘要 / diff / 技术栈 / 全局契约） |
| 设置 | 存储目录、日志持久化、主题、默认执行模式、并发上限、定时任务总开关、默认轮次、LLM 限速、dsh 配置、Agent 配置导入导出 |

核心流程：

```
拆解顶层需求 -> 技术总监输出【技术栈 + 全局契约 + 有序子任务 + 验收标准】
  ├─（人工审核开启）等待人工审批方案，通过后才创建子任务
  └─（人工审核关闭）直接生效
  ↓
按队列串行取当前子任务
  ↓
技术总监生成当前模块详细设计文档
  ├─（人工审核开启）等待人工逐一审批设计，通过后才允许 Coder 开工
  └─（人工审核关闭）自动通过
  ↓
Coder（dsh）写代码  -> 实时流式输出 + 捕获本轮 git diff
  ↓
Reviewer 评审【契约 + 已完成模块摘要 + 当前子任务 + 本轮 diff】
  ├─ 不通过 -> 轮次+1 -> 同一 Coder 修改（直到子任务最大轮次 -> 人工介入）
  └─ 通过   -> Coder 生成固定模板 summary.md -> Reviewer 单独校验摘要
                ├─ 不合格 -> 打回摘要（计轮次）
                └─ 合格   -> 落盘摘要 + 归档全部轮次 -> 子任务完成 -> 下一个子任务
  ↓
全部子任务完成 -> 全局评审【契约 + 所有摘要 + 全部模块 diff 汇总】
  ├─ 通过 -> 任务完成
  └─ 不通过 -> 问题归属到模块 -> 模块轮次重置为 1 -> 回到该模块增量评审 -> 再次全局评审
              （全局轮次耗尽 -> 人工介入）
```

### 1.1 V2 运行策略、存储与双通道

- **三种执行模式**：
  - **立即执行**：创建后自动启动管理者 Agent。
  - **稍后执行**：创建后停在「待运行」，点击【运行】才开始。
  - **定时执行**：只允许每日时间窗口内运行，例如 `01:00–06:00`；窗口结束自动暂停，下一窗口自动继续。已开始的模块会跑完当前轮次，新模块等待下一个窗口。支持跨午夜窗口、任务级开关和运行中修改窗口。
- **外部存储**：任务数据库、运行日志、模块设计 / diff / summary 快照统一保存在设置页指定的存储根目录，默认在应用数据目录，绝不写入项目目录。切换存储目录时会自动生成数据库一致性快照并迁移，旧目录保留。
- **日志持久化开关**：开启时保存 Agent 对话、工具调用、评审与修改历史；关闭时只在当前页面实时展示，不写入数据库（仍保留任务/模块等核心状态）。
- **浅色 / 深色主题**：顶栏和设置页均可切换，选择持久保存。
- **任务需求双入口**：新建任务时填写；运行中可在工作台「📝 需求」随时修改顶层需求和验收标准，变更会注入下一个 Agent 步骤。
- **流水线 vs 临时问答**：
  - 任务流程通道：需求 → 拆解 → Coder → 评审，按原有自动流水线执行。
  - 临时问答通道：工作台「💬 问答」打开独立会话，直接问技术总监问题，**不会触发子任务派发或自动开发**，与流水线上下文隔离。
- **暂停 / 终止 / 继续**：暂停可恢复；终止后不再派发任何新子任务，但历史数据与模块快照保留，之后可点击「继续任务」从当前进度恢复，已完成模块不会重跑。
- **人工介入面板**：模块轮次耗尽后，页面顶部会显示「需要人工介入」面板，包含最近评审意见、当前轮次，并提供：
  - **强制通过当前评审**：代码评审通过后继续生成摘要；摘要校验通过后直接完成模块。
  - **驳回并重做**：填写意见后让 Coder 重做，并自动为这一轮补足预算。
  - **追加轮次继续**：保留全部历史，从失败阶段自动继续执行 1/2/3/5 轮。
  - 任务列表也会显示「处理人工介入」入口。
- **并发与限速**：设置页可限制最大并发任务数与 LLM 每分钟请求数；超出的任务进入等待队列。
- **Agent 会话日志**：中栏时间线默认只展示评审者 / Coder 的关键发言、评审结论、模块设计、摘要与代码变更，**工具调用默认收起**（工具栏「▸ 工具调用（N）」可展开）；完整原始 LLM 请求/响应、工具结果、dsh 原始事件收进「原始事件」。
- **运行中改配置**：工作台「⚙ 配置」弹出配置弹窗，可修改模块轮次、全局轮次、人工审核、执行模式和定时窗口；取消不保存。
- **方案 / 逐模块设计审批**：开启人工审核后，拆解方案和每个模块设计都需要人工同意，Coder 才能开工。

### 1.2 任务完成后追加需求（V2.2）

任务进入「已完成」后，工作台和任务列表都会出现「＋ 追加需求」入口：

1. 输入新的问题或需求，选择处理方式：
   - **自动判断（推荐）**：评审者先梳理增量，简单改动只创建 1 个子任务；只有确实包含多个独立交付物时才拆成 2–6 个模块。
   - **单模块快改**：强制只生成 1 个子任务，适合小功能、修 bug、样式/文案调整。
2. 新增需求会追加到顶层需求历史中，评审梳理结论同步记录到 Agent 会话。
3. 保留原有技术栈、全局契约、全部已完成模块和评审历史，**不会重跑已完成模块，也不会重新拆解整个项目**。
4. 新模块沿用原有串行流程：模块设计 → Coder 编码 → 代码评审 → 摘要校验。
5. 新模块完成后会开启新一轮全局评审（`global_review_cycle + 1`），全局轮次重新计算；旧的全局评审记录仍保留可回看。
6. 如果梳理失败，输入内容不会丢失，可点击「运行 / 重试」再次梳理。

> 已确认的业务约定（代码即按此实现）：
> 1. 新建任务可多选 Coder，但串行版**所有子任务固定交给可选列表中的第一个 Coder**。
> 2. 全局评审驳回后，被返工模块的 **current_round 重置为 1**，重新获得完整 `module_max_round` 预算。
> 3. 摘要校验的上下文 = 全局契约 + 当前子任务验收标准 + **已通过的代码 diff** + summary 内容。
> 4. 轮次语义：Coder 首次实现为第 1 轮；代码返工、摘要返工、人工驳回都会使轮次 +1；达到 `module_max_round` 仍不通过则标记人工介入。全局轮次按“全局评审次数”计。模块设计生成/人工审批不计入代码轮次。

### 1.3 迭代版本与工作台信息架构（V2.3）

- **迭代 = 版本**：任务首次创建即为 `dev-1.0`；之后每追加一次需求新增一个迭代：
  - 默认**小版本 +1**：`dev-1.1`、`dev-1.2`……
  - 如果本次追加需求被拆出的**子任务超过 5 个**，直接**大版本 +1** 且小版本归零：`dev-1.2 → dev-2.0`。
  - 版本号在子任务数量确定后才落定；梳理过程中显示「待定」，不会出现半截版本号。
- **任务详情第一屏是迭代列表**，按版本倒序展示每个迭代的：需求原文、开始/结束时间、任务数（已完成/总数）、耗时、token（当前版本预留，显示「未统计」）、状态与评审梳理结论。点击某个迭代才进入该迭代的工作台，只展示该迭代范围内的子任务、对话与日志。
- **工作台信息架构**：
  - **中栏是主体**：顶部固定「方案与契约」按钮条（顶层需求 / 验收标准 / 技术栈 / 全局契约 / 当前模块设计），点击即在右栏预览；下方是按时间排列的**评审者与 Coder 完整对话**——Coder 完成汇报、评审结论、让 Coder 继续下一个子任务的指令、模块设计与摘要、人工介入消息全部保留，每条都带时间与角色。
  - **工具调用默认收起**：工具栏提供「▸ 工具调用（N）」开关，展开后以单行折叠形式展示，不再淹没正文。
  - **右栏是预览面板**：点击对话中的「模块设计方案 / 模块完成摘要 / 代码变更」，或在左栏点击模块的「设计」按钮，详情在右栏展示，类似 harness / Codex 的预览。
  - **左栏是迭代树**：按版本分组，默认展开当前迭代；每个子任务下提供「查看」（只看该模块的主要对话、不含工具调用）与「设计」（在右栏打开设计方案）按钮。
- **配置弹窗化**：工作台「⚙ 配置」由原来的页面内下拉改为弹窗，取消不保存、保存后立即生效（运行中同样生效）。
- **主题可读性**：按钮配色全部收敛为 CSS 变量（背景/前景/边框/悬停/禁用），浅色主题下禁用态与主按钮不再出现「透明背景 + 白色文字」。
- **日志持久化缺失时**：若该迭代创建时未开启日志持久化，工作台会明确提示「该迭代没有持久化日志」，而不是静默空白。

## 3. 环境要求

- macOS / Windows / Linux（当前开发环境 macOS）
- Node.js ≥ 20
- Rust stable ≥ 1.77
- Xcode Command Line Tools（macOS）
- Git
- **Harness CLI `dsh`** 已安装并在 PATH 中（或稍后在设置里填绝对路径，例如 `/opt/homebrew/bin/dsh`）
- 可用的模型 API Key

首次安装：

```bash
cd AgentCrew
npm install
```

启动开发模式：

```bash
npm run tauri dev
```

构建安装包：

```bash
npm run tauri build -- --bundles app   # 推荐：只构建 .app，最快
# 或完整构建：npm run tauri build
```

`.app` 产物在 `src-tauri/target/release/bundle/macos/AgentCrew.app`。
macOS 上如果没有「自动化/屏幕录制」权限，DMG 打包脚本可能卡在 AppleScript；使用 `--bundles app` 可绕过。

> 前端单独构建：`npm run build`；Rust 检查：`cd src-tauri && cargo check`；端到端测试：`cd src-tauri && cargo test`。

> 如果新开终端找不到 `cargo`，先执行 `source "$HOME/.cargo/env"`。

## 4. 配置与使用

### 4.1 配置 Agent

进入 **Agent 配置**：

- 至少创建 1 个 `Reviewer`、1 个 `Coder`。
- 服务商/协议支持：
  - OpenAI 兼容（DeepSeek / OpenAI / 其他兼容网关）
  - Anthropic Messages
- `baseUrl` 填到版本前缀即可，例如：
  - `https://api.deepseek.com/v1`
  - `https://api.openai.com/v1`
  - `https://api.anthropic.com`
- `apiKey` 仅保存于本机 SQLite 明文（导入导出 JSON 也是明文，请妥善保管）。
- Reviewer 直连 HTTP；Coder 的配置会被写入临时 dsh provider patch。

### 4.2 新建任务

进入 **任务列表 -> 新建任务**：

- 任务名称
- 顶层业务需求（大输入框）
- 项目验收标准
- 选择 1 个 Reviewer（只展示 reviewer 角色）
- 多选 Coder（串行版固定使用第一个）
- 单个子任务最大迭代轮次
- 全局评审最大轮次
- 项目本地工作目录（会真实写代码，建议是空目录或已有项目）
- **执行模式**：立即执行 / 稍后执行 / 定时执行（定时模式可设置每日窗口和开关）
- 人工审核模式（可选）

任务创建后默认**不自动启动**；只有选择「立即执行」或稍后手动点【运行】、或命中定时窗口才会启动。启动时会：

1. 自动创建目录（如不存在）；
2. 若还不是 git 仓库则 `git init`；
3. 用临时 git index 对工作目录做 tree 快照，作为 diff 基线（不改动用户真实 index）。

### 4.3 Workbench 操作

1. 打开任务先进入**迭代列表**（按版本倒序）：每个版本展示需求、起止时间、任务数、耗时、token（未统计）与状态；点击「进入迭代 →」才进入该版本的工作台，左上角 `←` 可返回迭代列表。
2. 左栏是**迭代树**：按版本分组，默认展开当前迭代；点击子任务选中，子任务下「查看」= 只看该模块的主要对话（自动隐藏工具调用），「设计」= 在右栏打开该模块设计方案。
3. 中栏顶部「方案与契约」按钮条：顶层需求 / 验收标准 / 技术栈 / 全局契约 / 当前模块设计，点击后在右栏预览；右侧「原始事件」查看完整审计流。
4. 中栏主体是**评审者与 Coder 的完整对话时间线**：按时间展示角色、类型与内容，子任务切换处有分隔标题；工具调用默认收起，可一键展开。
5. 右栏是**预览面板**：展示设计方案 / 摘要 / diff / 契约等详情，可关闭；未选择时显示当前模块快捷入口。
6. 顶部按钮：配置（弹窗）、需求、问答、运行/暂停/恢复、终止；定时任务在窗口外显示「等待时间窗口」。
- 方案审批阶段左侧展示待审批模块；设计审批阶段中栏展示技术总监的模块详细设计。
- 中间顶部固定操作台：方案/设计审批、人工强制通过/驳回、全局人工兜底会根据状态自动切换，不会被长内容顶出视野。
- 中间底部是人工消息输入框（Ctrl+Enter 发送）与待注入消息列表。
- 右侧可折叠查看任务需求、Agent 会话、技术栈、全局契约、已完成模块摘要和系统事件日志。
- 顶部「⚙ 配置」「📝 需求」「💬 问答」「运行/暂停/恢复/终止」可随时使用；任务完成后顶部和操作台会出现「＋ 追加需求」。
- 任务完成后，左侧模块恢复可点击，可回看每个模块的 diff、摘要和历史轮次；无需为了查看历史而重新运行。
- 进入全局评审后：顶部标签切换，左侧队列冻结，中间切换全局评审会话视图。
- 人工兜底：
  - **人工强制标记通过**：代码评审阶段会继续生成摘要；摘要校验阶段则直接完成模块。
  - **人工驳回，手动输入修改意见**：把意见交给同一 Coder 重做，轮次 +1。
  - 全局轮次耗尽时，可“人工强制通过全局评审”或“人工指定模块返工”。
  - 应用重启/线程中断后，可点击“恢复”从 SQLite 持久化状态继续；暂停和终止的区别见下方 V2 说明。

## 5. Harness CLI（dsh）对接说明

### 5.1 调用入口

每次 Coder 执行，应用调用：

```bash
dsh --profile headless \
    --patch <APP_DATA>/runtime/coder-<agentId>-patch.yml \
    --json -
```

- prompt 通过 **stdin** 传入（避免超长命令行参数）。
- 工作目录 = 任务选择的项目本地工作目录。
- stdout 是 NDJSON 事件流，应用从中读取 `{"type":"final","text":...}`。
- 执行前设置环境变量：
  - `DSH_AGENT_API_KEY=<该 Coder 的 apiKey>`
  - `DSH_PERMISSION_MODE=danger-full-access`（headless 无人值守，允许写文件/执行 bash；仅在你选择的项目目录内运行）
  - `DSH_PROFILE=headless`

### 5.2 按 Coder Agent 生成 dsh patch

应用会为每个 Coder 生成临时 patch，把该 Agent 的模型配置注入 dsh：

```yaml
- id: llm-pi-ai
  name: "@deepseek-ai/dsh-llm-pi-ai"
  config:
    providers:
      orchestrator-coder:
        displayName: "Coder 名称"
        apiKeyEnv: DSH_AGENT_API_KEY
        api: openai-completions        # anthropic 时自动切换 anthropic-messages
        baseURL: "https://api.deepseek.com/v1"
        models:
          - id: "deepseek-chat"
            name: "deepseek-chat"
            contextWindow: 200000
- id: agent-default-model
  name: "@deepseek-ai/dsh-agent-default-model"
  config:
    provider: orchestrator-coder
    model: "deepseek-chat"
```

> ⚠️ **temperature**：Reviewer 直连请求会使用配置值；dsh 当前不暴露 temperature 透传入口，因此 Coder 的 temperature 由 dsh/模型侧默认值决定。这是 Harness CLI 侧限制，不是业务漏实现。

### 5.3 diff 捕获

- 每轮 Coder 前后，用 **独立临时 git index**（`GIT_INDEX_FILE`）执行 `read-tree --empty + add -A + write-tree`，得到 tree hash。
- `git diff <beforeTree> <afterTree>` 得到本轮真实 diff（含新增文件），**不修改用户真实 index、不自动 commit、不做冲突合并**。
- 全局评审使用任务启动基线 tree 到当前 tree 的累计 diff。
- diff 传给 LLM 前会截断（90k / 140k 字符），避免上下文爆炸。

### 5.4 summary.md

- Coder 在项目内临时写入：`<work_dir>/summaries/<NN>-<module-slug>.md`
- 固定模板（六段，必须完全一致）：

```markdown
# 模块名称
1. 对外接口列表：接口路径、请求方式、入参、返回字段
2. 关联数据库表
3. 核心业务逻辑简述
4. 对外依赖（依赖哪些其他模块能力）
5. 本模块对外提供的能力（哪些其他模块会调用我）
6. 已知限制、边界、未实现能力
```

- Reviewer 单独校验摘要并返回 JSON；通过后应用把摘要快照移动到外部存储目录 `<storage_root>/tasks/<task_id>/modules/.../summary.md`，删除项目内的临时文件，并把内容写入 DB、归档全部轮次。最终模块快照不会留在项目目录。
- 摘要只作为后续评审上下文，**历史完整对话/旧代码永远不会进入 Reviewer 上下文**。
- 应用会先做一次确定性模板校验（六个标题、长度、禁止代码围栏），再做 LLM 摘要准确性校验。

## 6. 数据存储

V2 的存储根目录可在设置页自定义，默认仍为应用数据目录：

- 默认（macOS）：`~/Library/Application Support/com.local.agent-orchestrator/`
- 默认（Windows）：`%APPDATA%/com.local.agent-orchestrator/`
- 自定义目录：`<storage_root>/orchestrator.db`、`<storage_root>/tasks/<task_id>/...`
- 应用显示名是 **AgentCrew**；bundle identifier 保留 `com.local.agent-orchestrator`，用于兼容升级前已有的本地数据库。
- 所有数据本地存储，不上云。建表 SQL 见 [`docs/schema.sql`](docs/schema.sql)。

模块快照结构：

```
<storage_root>/
├─ orchestrator.db
├─ runtime/                    # dsh provider patch
└─ tasks/<task_id>/
   └─ modules/01-模块名/
      ├─ design.md             # 模块设计快照
      ├─ summary.md            # 通过验收的摘要快照
      └─ rounds/
         ├─ round-01.diff
         ├─ round-01-code-review.json
         └─ ...
```

切换存储目录时会用 `VACUUM INTO` 生成一致性数据库快照，并复制任务快照与历史备份到新目录；旧目录不会删除。

表：

| 表 | 用途 |
| --- | --- |
| `agent_config` | Agent 配置 |
| `task_main` | 任务主表（含技术栈、全局契约、阶段、状态、人工审核开关、待审批方案、git 基线 tree） |
| `iteration` | **任务迭代（版本）**：版本号、需求、梳理结论、起止时间、状态、token 预留字段 |
| `subtask` | 子任务 / 模块（含详细设计、summary、全部轮次 JSON 归档、所属 iteration_id） |
| `task_log` | 高层系统事件日志 |
| `task_event` | **全量执行输出**（LLM 请求/响应、dsh 流、diff 等，页面实时展示） |
| `human_message` | 人工随时输入的消息队列（pending / consumed） |
| `chat_message` | 临时问答会话消息（每任务独立，不进入流水线） |
| `app_setting` | 存储、日志、主题之外的运行设置键值 |

> 旧版本数据库启动时会自动执行 `ALTER TABLE` 补齐新列并创建新表，**不会删除或重建已有 Agent、任务、子任务数据**。

`iteration_record` 按需求内嵌在 `subtask.iteration_records` JSON 中，不单独分表。

> V2.3 升级：旧任务的子任务、日志与事件会自动归档进自动创建的 `dev-1.0` 迭代，迁移幂等、不丢失任何历史数据。token 统计尚未接入（字段预留 `token_total = -1`，界面统一显示「未统计」）。

## 7. LLM 结构化输出

- Planner / Reviewer / 全局评审全部要求 **只返回 JSON**。
- Coder 不解析自由文本：代码结果通过 git tree diff 获取，摘要通过固定文件路径读取，因此不存在“解析 Coder 回复失败”的问题。
- OpenAI 兼容请求带 `response_format: {"type":"json_object"}`；若服务端不支持会自动降级重试。
- 解析层会：
  - 提取 Markdown 围栏内 JSON；
  - 处理前后解释文字；
  - 首次解析失败自动发起一次“JSON 修复”请求；
  - 结构/语义不合法（如 `passed=false` 但无 feedback）会重试一次。
- 仍未通过则任务标记 `failed`，日志写明原因，可人工恢复。

主要 JSON 约定：

```json
// Planner
{ "global_contract": "markdown", "subtasks": [ { "name": "...", "accept_criteria": "..." } ] }

// 单次评审
{ "passed": true, "feedback": "..." }

// 全局评审
{ "passed": false, "feedback": "...", "issues": [
  { "subtask_id": 3, "subtask_name": "用户鉴权模块", "feedback": "..." }
] }
```

## 8. 常见问题

**Q: 点击开始任务后立即失败，日志提示启动 dsh 失败？**
GUI 应用的 PATH 通常不包含 Homebrew。到设置页把 `dsh 可执行文件` 填成绝对路径（`which dsh` 的结果，例如 `/opt/homebrew/bin/dsh`）。

**Q: Coder 报 401 / MISSING_CREDENTIAL？**
检查该 Coder Agent 的 apiKey / baseUrl / model；应用通过 `DSH_AGENT_API_KEY` 注入，dsh 自身的 DeepSeek 凭据不参与。

**Q: 我想让技术总监先给我审方案和设计怎么办？**
新建任务时勾选「开启人工审核模式」，或运行中在「⚙ 配置」里打开。之后方案与每个模块设计都会等待你同意；关闭时会自动放行正在等待的方案/设计。

**Q: 执行过程看不到详细输出？**
右栏「Agent 会话」默认展示 Agent 关键对话、评审结论、工具调用和代码变更；点「工具」只看工具调用，点「全部」查看更多事件，点「原始事件」可查看完整 LLM/dsh 审计流。旧任务若没有结构化事件，可在原始事件中看到历史数据。

**Q: 拆解/评审报 `HTTP 404` 或 `HTTP 400`？**
优先检查 `model 名称` 是否填了服务商 API 的 **model ID**，而不是界面展示名。DeepSeek 官方当前支持 `deepseek-flash`、`deepseek-v4-pro`。错误日志现在会带实际请求 URL 和响应体，可据此检查 baseUrl 是否多写/少写 `/v1`。

**Q: Reviewer 报 JSON 解析失败？**
确认所用模型支持 JSON 输出；应用会自动重试一次并降级 `response_format`，仍失败请更换模型或降低 temperature。

**Q: 子任务不动了 / 应用重启后状态一直“执行中”？**
应用重启会把中断任务标记为 `failed` 并写日志；到工作台点击“恢复”。如果已到轮次上限，会显示“等待人工介入”，使用人工通过/驳回。

**Q: 工作目录必须是 git 仓库吗？**
不需要。应用会自动 `git init`。但建议已有项目保留自己的 `.git`；应用不会 commit、不会改你的真实 index。

**Q: 会并行开发多个模块吗？**
不会。简单版强制串行，一次只处理一个子任务。

## 9. 明确不做（需求硬约束）

- ❌ 自动 git 冲突合并
- ❌ MCP 插件市场 / 额外插件体系
- ❌ 内置代码编辑器 / 内置终端
- ❌ 复杂依赖拓扑编排（只有有序串行队列）
- ❌ 多用户 / 登录系统
- ❌ 向量 RAG / 自动摘要历史对话
- ❌ 并行开发多个子任务
- ❌ 任何云端存储
- ⏳ token 用量统计与计费（V2.3 只预留 `iteration.token_total` 字段，界面统一显示「未统计」）

## 10. 手工验收清单

1. 创建 Reviewer + 2 个 Coder，刷新后仍存在。
2. 新建任务，选择 Reviewer / 多 Coder / 轮次 / 工作目录，启动。
3. 工作台左侧出现有序子任务；右侧契约已生成。
4. Coder 产生的代码真实出现在工作目录；中间出现 diff。
5. 评审不通过：轮次 +1，同一 Coder 收到修改意见并重做。
6. 代码通过：生成 summary.md；摘要校验通过后子任务 ✅，自动进入下一个。
7. 子任务卡片展开可看到每一轮评审意见 + diff + 结论。
8. 全部完成后自动进入全局评审；左侧冻结、中间切换视图。
9. 全局轮次耗尽显示人工介入；人工通过后任务完成。
10. Agent 配置导出再导入成功；设置保存后重启仍保留。
11. 运行中修改轮次上限，后续评审立即按新上限执行。
12. 开启人工审核：拆解后停在方案审批；同意后每个模块设计逐一等待审批，同意后才开始编码。
13. 暂停后 dsh 立即停止，任务显示「已暂停」且可恢复；终止后不再派发新子任务，但可点击「继续任务」从当前进度恢复。
14. 输入人工消息后，下一个 Agent 步骤的 LLM 请求/事件流中能看到“人工消息已注入”。
15. 中栏对话时间线持续刷新，显示评审者/Coder 关键对话、评审结论、模块设计与摘要；工具调用默认收起、可展开；原始事件可单独展开。
16. 新建任务选择「稍后执行」，创建后停在待运行，点击运行才启动。
17. 新建任务选择「定时执行」并设置窗口，窗口外不派发新模块，窗口内自动继续。
18. 设置页切换存储目录后，新任务数据与模块快照写入新目录，旧目录保留。
19. 关闭日志持久化后，页面仍实时显示事件，但重新打开任务不保留这些运行日志。
20. 在设置页/顶栏切换浅色/深色主题，重启后保持。
21. 临时问答对话不会创建子任务或改变任务状态。
22. 运行中修改需求/验收标准，下一个 Agent 请求包含最新内容。
23. 模块轮次耗尽后，顶部出现「需要人工介入」面板，强制通过 / 驳回 / 追加轮次按钮可点击。
24. 任务终止后，任务列表和工作台都出现「继续」入口；继续后停在待人工处理模块，并恢复全部历史。
25. 任务完成后，工作台和任务列表都出现「追加需求」入口；提交后评审者先梳理增量，不重新拆解已完成项目。
26. 追加一个简单需求时只新增 1 个子任务；选择「单模块快改」时，即使评审认为复杂也必须只生成 1 个子任务。
27. 追加需求完成后，新模块走完设计/编码/评审/摘要流程，全局评审进入第 2 次迭代；旧模块和旧评审记录完整保留。
28. 任务详情第一屏是迭代列表且按版本倒序；`dev-1.0` 显示首次需求，追加后新增 `dev-1.1`。
29. 单次追加需求拆出超过 5 个子任务时，新版本号直接变为 `dev-2.0`，小版本归零。
30. 旧数据库启动后，历史任务的子任务与日志全部归入自动创建的 `dev-1.0`，重复启动不产生重复迭代。
31. 点击不同迭代，只显示该迭代范围内的子任务、对话与日志；无日志持久化的迭代给出明确空状态。
32. 点击子任务「设计」或对话中的「模块设计方案」，右栏出现设计方案预览。
33. 点击子任务「查看」，中栏只显示该模块的对话内容（不含工具调用），并可一键取消过滤。
34. 工作台「⚙ 配置」以弹窗展示；取消不保存、保存后立即生效。
35. 浅色主题下所有按钮（默认/悬停/禁用/主按钮/危险按钮）文字与背景对比清晰，无「透明背景 + 白字」。
